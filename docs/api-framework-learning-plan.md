# API Framework Learning Plan

This plan is designed for a beginner. The target is not just to run tests. The target is to understand why each layer exists and then write your own tests without guessing.

## Learning Goal

By the end of this plan, you should be able to:

- explain the full API test flow in this repo
- read and understand a mock API contract
- create request payloads with builders
- use Playwright API clients and fixtures correctly
- write happy-path and negative-path API tests
- extend the framework with one new module by yourself

## Before You Start

You only need these basics:

- how to open files in the repo
- how to run terminal commands
- very basic JavaScript or TypeScript syntax

If HTTP is new to you, start with:

- [docs/01-http-api-testing-basics.md](/Users/user/projects/Playwright-api/docs/01-http-api-testing-basics.md)

## Framework Map

This repo is intentionally layered:

1. mock server
2. models
3. builders
4. API clients
5. fixtures
6. assertions
7. tests

The correct way to learn it is from the bottom of the business flow upward, not by jumping between files randomly.

## Step-by-Step Teaching Plan

### Step 0: Environment Setup

Goal:

- make the repo runnable locally

Do:

1. run `npm install`
2. run `npm run test:api`

Learn:

- Playwright can run API tests without a browser UI
- the mock server starts automatically from the Playwright config

Done when:

- the suite runs locally without missing-package errors

### Step 1: Learn HTTP Through the Mock API

Files:

1. [docs/01-http-api-testing-basics.md](/Users/user/projects/Playwright-api/docs/01-http-api-testing-basics.md)
2. [api-mock/server.mjs](/Users/user/projects/Playwright-api/api-mock/server.mjs)

Focus:

- endpoints
- methods
- auth
- request validation
- status codes
- business rules

Practice:

- list every endpoint in the server
- write down which ones require auth

Done when:

- you can explain what `POST /payments` and `POST /payments/:id/refunds` do without reading the code

### Step 2: Learn the Data Contract

Files:

1. [api/core/models/payment.model.ts](/Users/user/projects/Playwright-api/api/core/models/payment.model.ts)

Focus:

- request types
- response types
- why typed contracts reduce mistakes

Practice:

- identify which fields belong only to requests
- identify which fields are generated by the server

Done when:

- you understand why `PaymentResponse` extends `PaymentRequest`

### Step 3: Learn the Smallest Useful Test

Files:

1. [api/tests/payments/create-payment.spec.ts](/Users/user/projects/Playwright-api/api/tests/payments/create-payment.spec.ts)

Focus:

- test structure
- arrange, act, assert
- transport assertions vs business assertions

Practice:

- read one test and explain each line
- identify where data comes from and where assertions happen

Done when:

- you can explain why `expect(response.status()).toBe(201)` and `PaymentAssertions.isAuthorizedPayment(payment)` both exist

### Step 4: Learn Builders

Files:

1. [api/core/builders/payment.builder.ts](/Users/user/projects/Playwright-api/api/core/builders/payment.builder.ts)

Focus:

- default test data
- overrides
- readable test setup

Practice:

1. add a GBP payment builder variation
2. add a custom email variation

Done when:

- you can create test payloads without hardcoding raw JSON inside every test

### Step 5: Learn API Clients

Files:

1. [api/core/clients/base.api.ts](/Users/user/projects/Playwright-api/api/core/clients/base.api.ts)
2. [api/core/clients/auth.api.ts](/Users/user/projects/Playwright-api/api/core/clients/auth.api.ts)
3. [api/core/clients/payments.api.ts](/Users/user/projects/Playwright-api/api/core/clients/payments.api.ts)

Focus:

- why request logic should not live in specs
- how endpoint changes stay isolated
- which methods return raw `APIResponse` and which return parsed JSON

Practice:

1. trace the login flow from test to server
2. trace the refund flow from test to server

Done when:

- you can explain why the client layer exists even in a small project

### Step 6: Learn Fixtures

Files:

1. [api/core/fixtures/api.fixture.ts](/Users/user/projects/Playwright-api/api/core/fixtures/api.fixture.ts)

Focus:

- shared setup
- dependency injection into tests
- reusable auth token management

Practice:

- explain how `authApi`, `paymentsApi`, and `authToken` become available in every test

Done when:

- you understand why fixtures remove duplication without hiding too much logic

### Step 7: Learn Reusable Assertions

Files:

1. [api/core/assertions/payment.assertions.ts](/Users/user/projects/Playwright-api/api/core/assertions/payment.assertions.ts)

Focus:

- reusable business checks
- keeping assertions expressive
- difference between data shape checks and business-state checks

Practice:

- add one new assertion for partially refunded payments

Done when:

- you stop repeating the same field checks across multiple tests

### Step 8: Learn Negative Testing

Files:

1. [api/tests/payments/create-payment.spec.ts](/Users/user/projects/Playwright-api/api/tests/payments/create-payment.spec.ts)
2. [api/tests/payments/refund-payment.spec.ts](/Users/user/projects/Playwright-api/api/tests/payments/refund-payment.spec.ts)

Focus:

- invalid input
- business conflicts
- error messages
- why negative tests are as important as happy-path tests

Practice:

1. add a missing-token test
2. add an unsupported-currency test

Done when:

- you can choose the correct status code expectation for a failure case

### Step 9: Write One Test Yourself

Goal:

- create one new test without copying blindly

Recommended first custom tests:

1. `GET /health` returns `200`
2. refunding the full amount changes payment status to `REFUNDED`
3. fetching an unknown payment returns `404`

Rule:

- first write the test name
- then write expected status code
- then decide which layer needs to change, if any

Done when:

- your new test passes and the existing suite still passes

### Step 10: Extend the Framework

Goal:

- add one small feature end to end

Order:

1. update mock API if needed
2. add or update model
3. add builder if payload creation is needed
4. add client method
5. add fixture only if shared setup is needed
6. add assertion helpers if checks repeat
7. add tests

This is the exact pattern you should reuse for future modules.

## How I Would Teach You in Sequence

When we continue, I would teach in this order:

1. HTTP basics and request/response anatomy
2. the mock payment API contract
3. the first payment test
4. builders
5. clients
6. fixtures
7. assertions
8. negative tests
9. how to design a new module

That order matters. It keeps you from learning abstractions before you understand the problem they solve.
